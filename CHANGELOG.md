# Changelog

## [Unreleased]

- **Shadownet v0.2 consolidated spec.** Replaces v0.1 RFCs 0001–0009 with one wire spec (`rfcs/0001-shadownet.md`) plus companion specs for the MCP control surface (`rfcs/0002-shadownet-mcp.md`) and the onboarding URI (`rfcs/0003-shadownet-onboarding.md`). v0.2 is a profile of A2A 1.0 carrying a Shadownet envelope in extension metadata under `urn:shadownet:0.2`. The complete v0.1 → v0.2 delta:
  - Names resolved via DNS (one TXT per provider at `_shadownet.<domain>`) + signed AgentCard fetch. The HTTP-served per-Shadowname JWT records from v0.1 §SNS are removed.
  - Identifiers are bare Shadownames (`alice@sh4dow.org`), bare domains, and multibase Ed25519 public keys. DID method machinery (`did:key`, `did:web`, DID documents, `shadownet:delegatedIssuers`) removed entirely.
  - Credentials are plain JWTs with **one named kind**: `org_affiliation`. W3C VC wrapping, Verifiable Presentations, freshness proofs, and the L1/L2/L3/O1 personhood ladder all removed. The `personhood` and `org` kinds (carried into early v0.2 drafts) are also cut: cheap personhood ceremonies don't deliver uniqueness, strong ones don't deliver adoption, and §7.4 already relocated Sybil defense to Hubs. `org` is redundant with the trust store. Status list is a bare bitstring at `<iss>/.well-known/shadownet/status/<epoch>`; no `BitstringStatusList` VC.
  - Trust store collapsed to one surface (a flat `(issuer, accepted-kinds)` list). Default trust store ships **empty**; users populate as they join Hubs/orgs. Predicate language removed; acceptance policy is two kind lists (`fromContact`, `fromStranger`).
  - Envelope is one JWS in A2A `message.metadata["urn:shadownet:0.2"]`, bound to the surrounding message via `msgHash` (SHA-256 over canonical JSON minus the Shadownet metadata key). No session token, no `X-Shadownet-Presentation` header, no nonce challenge. JWS `typ` values are `shadownet-env+jwt`, `shadownet-cred+jwt`, `shadownet-csr+jwt`.
  - Receiver responses are A2A `Message` (not `Task`), inheriting A2A's agent-opacity principle: no quarantine state machine on the wire. Three receiver-side routes (inbox / stranger_review / rejected) but only the rejection is observable to senders.
  - Errors are RFC 7807 `application/problem+json` with `type` URN (`urn:shadownet:error:<code>`).
  - Receiver classification gains an **auto-add-on-outbound-initiated** rule: receivers SHOULD auto-add a sender when the inbound envelope's `contextId` matches a recent outbound from this Subject. Eliminates the cross-Sidecar approval round-trips in multi-party flows; safe because `contextId` is receiver-generated.
  - Same-provider-domain shortcut clarified: only valid when the provider domain operates as a single-tenant organization deployment, NOT for multi-tenant public providers.
  - Retry semantics made explicit: each retry MUST re-mint the envelope with fresh `iat`/`exp`/`messageId` (§8.10).
  - Reachability requirement stated explicitly: v0.2 requires always-on recipient endpoints; intermittent hosts use the gateway pattern. A normative MX-style provider-relay is a v0.3 candidate.
  - **Three custody tiers** named explicitly in §11: self-hosted, hybrid (BYO-key), fully managed. The middle tier — provider hosts the AgentCard, user holds the key — is the operationally interesting one for adoption.
  - CSR endpoint at `<iss>/.well-known/shadownet/issue` is idempotent within a ceremony; the v0.1 proof-session state machine and HMAC callback are removed.
  - Naming conventions made consistent: JSON field names camelCase, value strings (kinds, error codes) snake_case, URN suffixes snake_case, JWS `typ` kebab + `+jwt`.
  - Companion specs: MCP control surface (RFC 0002) defines the host-LLM ↔ Sidecar surface; onboarding URI (RFC 0003) defines `shadow://connect?ep=…&token=…`. v0.1's OAuth 2.1 profile (RFC-0009) is not carried over; opaque bearer tokens are sufficient for the local-only control plane.
  - The v0.1 RFCs 0001–0009 are deleted from the repo; the `v0.1-final` git tag preserves a stable reference for implementations still tracking that surface.
  - `examples/` directory deleted: v0.1 walkthroughs depended on Interaction Profiles, DIDs, and `social_*` MCP tools that no longer exist. Worked examples for v0.2 live in the spec appendices (Appendix B of RFC 0001).
  - `schemas/` directory rewritten for v0.2 wire artifacts (`schemas/credentials/{credential,csr}.schema.json`, `schemas/messages/envelope.schema.json`, `schemas/agentcard/shadownet-extension.schema.json`, `schemas/errors/problem.schema.json`). JSON Schema 2020-12. Consumed by the conformance suite at `shadownet-protocol/shadownet/conformance`. The v0.1 W3C-VC-shaped schemas (`subject-credential`, `affiliation-credential`, `integration-bundle`, `social-inbox-wait-result`, the old `envelope.schema.json` for the `shadownet/v1+envelope` part) are gone.
  - `GLOSSARY.md` and `ROADMAP.md` rewritten for v0.2 vocabulary and milestones.
  - **Direct addressing as first-class peer to Shadowname addressing.** v0.2 ships two equally-valid addressing modes: Shadowname mode (`alice@sh4dow.org`, DNS-resolved, provider-mediated) and direct mode (`shadow://key:z6Mk...@host:port`, no DNS, no provider). The Shadow's cryptographic identity is always the Ed25519 public key; the Shadowname is an optional human-readable alias bound to the key by a provider. This brings the protocol in line with the "anyone can be reachable; names are a convenience" principle (the web's IP-vs-domain model) and gives self-hosters a `docker compose up`-on-a-VPS path that doesn't require buying a domain or configuring DNS.
  - Single `shadow://` URI scheme with a `key:` userinfo type tag distinguishing the modes (`shadow://alice@sh4dow.org` vs `shadow://key:z6Mk...@host:port`). Optional `#sha256:<fingerprint>` URI fragment carries a TLS certificate pin for direct mode.
  - Direct-mode AgentCards are self-served at A2A's standard `<endpoint>/.well-known/agent-card.json` and self-signed by the Shadow's own key. TLS posture is pinned self-signed (TOFU on first connect, MUST-match against `#sha256:` pin when supplied); declared in the AgentCard's `securitySchemes` as `shadownet:pinned-self-signed`. The envelope JWS provides authoritative authentication regardless of TLS posture.
  - Credential identifiers (`iss`, `sub`, `org`) widen to accept either domains/Shadownames or bare public keys, enabling keyed Hubs and self-signed affiliation issuers.
  - Schema patterns updated to allow either Shadowname or multibase Ed25519 public key in identifier fields.
  - **RFC 0002 (MCP) made content-agnostic.** Removed §5 Intent Profiles entirely (the `coordinate_v1`, `confirm_plan_v1`, `accept_plan_v1` schemas and the `PlanObject` type with activity/when/where/participants fields). Removed the `coordinate`, `confirm_plan`, `accept_plan` tools. These prescribed a specific application interaction pattern ("propose a plan with location and time") at the MCP control-surface layer, which locks every implementation into one application semantic and replays v0.1's `social_coordinate` mistake. Application-level interaction schemas now live exclusively in separate intent profile companion specs (RFC 0004+) and reach the host LLM through the opaque `body.intent` / `body.data` slots on the generic `send` / `inbox` tools. The MCP surface in v0.2 is the control plane only: contact graph operations, envelope dispatch, inbox access, identity. It does not interpret body content. Identifier fields in tool inputs widened to accept Shadowname, `shadow://` URI, or bare key; `identity` tool returns both `shadowname` and `directUri` (whichever the Subject has). Section numbering re-sequenced after the removals.

- RFC-0005: added §Lifecycle defining the record time-validity contract. Pins the wire invariant that resolution responses MUST NOT carry a pre-expired envelope, defines two valid provider implementation patterns (re-issuance on resolve vs. store-and-serve), gives normative client-side renewal guidance (re-register before `iat + ttl - max(60, ttl/10)`), and recommends resolvers distinguish expiry from malformedness in their error taxonomy. Recommended default `ttl` raised from the previous ad-hoc 300 s to 3600 s. Wire shape unchanged.
- RFC-0007: removed `social_set_webhook` tool and webhook delivery path (Path 2). Inbound delivery is now MCP notifications (Path 1) or `social_inbox_wait` long-poll (Path 2, RECOMMENDED). The webhook HMAC/retry/URL-constraint sections, §Compatibility headers, and §Coexistence with webhooks are all removed. `social_inbox_wait` is now the RECOMMENDED default.
- RFC-0008: removed `webhook_secret` field from integration bundle and `webhook` capability flag. `inbox-wait` flag marked RECOMMENDED.
- RFC-0009: removed `social_set_webhook` from `mcp:tools.write` scope.
- Schemas: removed `webhook_secret` from `integration-bundle.schema.json`; removed webhook references from `social-inbox-wait-result.schema.json`.
- Examples: updated `birthday-flow.md` and `free-form-coordination.md` to use `social_inbox_wait` instead of webhook delivery.

- Initial v0.1 RFC set: 0001 Overview, 0002 Identity, 0003 Credentials, 0004 SCA, 0005 SNS, 0006 A2A Profile, 0007 MCP Tools.
- JSON Schemas for credential and A2A envelope.
- Wire-level Birthday-flow walkthrough (mixed deployment).
- RFC-0004: on-protocol proof flow (`/proof/start`, `/proof/status`, callbacks), `/freshness` request format, required-level predicate grammar.
- RFC-0004: clarified that proof `method` URIs are operator-defined; the protocol does not enumerate methods.
- RFC-0007: Sidecar→host-agent inbound notification contract (`social_inbox_wait`, MCP notifications).
- Canonical domain landed: `sh4dow.org`. All `shadownet.example` placeholders replaced across spec, schemas, and example.
- RFC-0009: new RFC defining the OAuth 2.1 authorization profile for the Sidecar's MCP endpoint. Strict superset of the MCP authorization specification — composes RFC 9728 (Protected Resource Metadata), RFC 8414 (AS Metadata), RFC 7636 (PKCE), RFC 8707 (Resource Indicators), and optionally RFC 7591 (DCR), RFC 7009 (Revocation), RFC 8628 (Device Grant), RFC 7662 (Introspection). Independent conformance class; coexists with RFC-0008 paste-based onboarding.
- RFC-0007 §Transport: amended to accept OAuth 2.1 access tokens (RFC-0009) as an alternative to RFC-0008 paste-based bearer tokens on the same MCP endpoint.
- RFC-0008: added `oauth-authorize` capability flag and the optional `protected_resource_metadata` bundle field.
- RFC-0006: `interaction` is now OPTIONAL. Default envelope form is free-form text (`payload.text` + optional `hints`); typed Interaction Profiles become an opt-in optimization for cases where structure prevents ambiguity. Schema updated; new `payload_invalid` error code added for callees that choose to enforce a known profile.
- RFC-0007: `social_send` `interaction` argument is now optional, mirroring RFC-0006. Payload guidance documents free-form vs. typed shapes.
- New example `examples/free-form-coordination.md`: companion walkthrough showing the default text-payload envelope (the Birthday flow remains the typed-path example).
- RFC-0008 (new): Sidecar Onboarding Surface. Defines the integration-bundle endpoint (`GET <base>/v1/account/me/integration-bundle`), the `shadownet://connect?...` URI scheme with inline and handoff forms, and content-negotiated per-host install pages at `<base>/connect/<host>`. Conformance is independent of RFC-0007 — a Sidecar MAY implement one without the other. The set of recognized host slugs lives as a non-normative companion at `examples/well-known-hosts.md`; adding a host does not require a spec change.
- RFC-0007: new required tool `social_inbox_wait` — long-poll for inbox events. `event_id` is opaque to clients; on empty timeout the cursor returns the server's current high-water mark (or `null` for tenants that have never had an event). The same event delivered via `social_inbox_wait` and Path 1 notifications MUST carry byte-identical `event_id` strings so receivers can dedupe across transports.
- RFC-0007: renamed Path 1 notification surface from the singular `shadownet/inbox` to the per-event namespace `notifications/shadownet/<event-name>` (`inbox.message`, `task.update`, `freshness.expired`, `presentation.failed`). This is a pre-v1.0 rename, not additive — Sidecars and host agents that implemented the old name must update. The receiver-idempotency requirement now keys on `event_id` rather than `messageId` so it generalizes to non-message events.
