# RFC 0004: Shadow Certificate Authority

## Summary

Defines what an SCA is, how it issues credentials (including the on-protocol proof flow), how it publishes its policy, and how verifiers decide which SCAs to trust at which levels using a small predicate language. The credential artifact itself is in [RFC-0003](./0003-credentials.md).

## SCA identity

An SCA is itself identified by a `did:web` DID. Its DID document MUST include at least one Ed25519 verification method used to sign credentials, freshness proofs, and proof-flow callbacks.

## Issuance flow

The protocol mirrors X.509 CSR semantics: the subject controls the keys; the SCA never sees a private key. Proof of personhood (or org control) happens via a structured **proof session** between the subject and the SCA, replacing the older off-protocol assumption.

```
Subject                                                SCA
   │                                                   │
   │ 1. GET  /.well-known/sca/policy.json ──────────► │
   │ ◄────── policy ──────────────────────────────────│
   │                                                   │
   │ 2. POST /proof/start  (level, subject DID) ────► │
   │ ◄────── { sessionId, method, next: { … } } ─────│
   │                                                   │
   │ 3. (out-of-band) user completes proof            │
   │     (clicks email, uploads ID, books in-person…) │
   │                                                   │
   │ 4. POST /proof/status  (sessionId) ────────────► │   (or webhook callback)
   │ ◄────── { status: "ready" } ─────────────────────│
   │                                                   │
   │ 5. POST /issuance  (CSR JWT, sessionId) ───────► │
   │ ◄────── credential JWT ──────────────────────────│
```

Step 3 is *user* work, not protocol — clicking a Stripe Identity link in a browser, for example. Steps 1, 2, 4, 5 are all on-protocol and specified below.

## Endpoints

A v0.1 SCA MUST expose:

| Path | Method | Purpose |
| --- | --- | --- |
| `/.well-known/did.json` | GET | DID document (per [RFC-0002](./0002-identity.md#did-web--organizations)). |
| `/.well-known/sca/policy.json` | GET | Issuance policy (below). |
| `/proof/start` | POST | Open a proof session at a specified level. |
| `/proof/status` | POST | Poll a proof session's state. |
| `/issuance` | POST | Submit a CSR backed by a `ready` proof session; receive a credential. |
| `/freshness` | POST | Request a [freshness proof](./0003-credentials.md#lifetimes-and-freshness) for a credential `jti`. |
| `/status/<list-id>` | GET | A [BitstringStatusList](./0003-credentials.md#revocation) credential. |

All endpoints MUST be served over TLS 1.3.

### Common: subject authentication

Every authenticated request to `/proof/*`, `/issuance`, or `/freshness` carries:

```
Authorization: Bearer <subject-auth JWT>
```

Where the subject-auth JWT is signed by the subject's key:

```json
{
  "alg":"EdDSA","typ":"JWT","kid":"<subject DID>#<key id>"
}
```
```json
{
  "iss": "did:key:z6MkSubjectPubkey...",
  "aud": "did:web:sca.shadownet.example",
  "iat": 1756680000,
  "exp": 1756680060,
  "jti": "<uuid>",
  "shadownet:v": "0.1",
  "purpose": "sca-request"
}
```

`exp - iat` MUST be ≤ 60 s. The SCA MUST verify the signature against the `iss` DID and reject if `aud` is not its own DID.

### `POST /proof/start`

Opens a proof session at a requested level. The SCA returns a `sessionId` and a method-specific instruction for completing the proof.

Request body:

```json
{
  "shadownet:v": "0.1",
  "subject":     "did:key:z6MkSubjectPubkey...",
  "level":       "urn:shadownet:level:L2",
  "callbackUrl": "https://my.sidecar.example/proof/callback"
}
```

`callbackUrl` is OPTIONAL. If present, the SCA SHOULD POST a notification on completion (see Callbacks below).

Response (`200 OK`):

```json
{
  "shadownet:v": "0.1",
  "sessionId":   "ses-01H9...",
  "expiresAt":   1756683600,
  "method":      "stripe-identity-document-check-v1",
  "next": {
    "kind": "redirect",
    "url":  "https://verify.stripe.com/abc123",
    "ttl":  600
  }
}
```

`method` MUST equal one of the `method` values declared in the SCA's policy document for the requested level.

`next.kind` is one of:

| `kind` | Meaning |
| --- | --- |
| `redirect` | Open `next.url` in a browser. |
| `embed` | Render `next.url` in an iframe (some methods). |
| `email-link` | The SCA emailed the subject a link; user clicks it. No URL returned. |
| `in-person` | Out-of-band scheduling; SCA contacts subject offline. |

Errors:

| Status | Code | Meaning |
| --- | --- | --- |
| `400` | `invalid_level` | Level URI not offered by this SCA. |
| `403` | `subject_blocked` | Subject DID has been banned from this SCA. |
| `429` | `rate_limited` | See policy `rateLimit`. |

### `POST /proof/status`

Polls a session.

Request:

```json
{ "shadownet:v": "0.1", "sessionId": "ses-01H9..." }
```

Response (`200 OK`):

```json
{
  "shadownet:v": "0.1",
  "sessionId":   "ses-01H9...",
  "status":      "pending"
}
```

`status` is one of `pending`, `ready`, `failed`, `expired`. Once `ready`, the session is consumed by the next successful `/issuance` call carrying the same `sessionId`.

### `POST /issuance`

Submit a CSR backed by a `ready` session.

Request:

```json
{
  "shadownet:v": "0.1",
  "csr":         "<CSR JWT>",
  "sessionId":   "ses-01H9..."
}
```

The **CSR** is a JWT signed by the subject's key:

```json
{
  "iss": "did:key:z6MkSubjectPubkey...",
  "iat": 1756680000,
  "exp": 1756680600,
  "aud": "did:web:sca.shadownet.example",
  "request": {
    "level":       "urn:shadownet:level:L2",
    "subjectType": "person"
  }
}
```

The SCA verifies, in order:

1. Subject-auth JWT (header `Authorization`).
2. CSR JWT signature against `csr.iss`.
3. `csr.aud` matches the SCA's own DID.
4. `csr.iss` matches the subject DID bound to `sessionId` in `/proof/start`.
5. `csr.request.level` matches the level requested at `/proof/start`.
6. The session is in `ready` state and not expired.

If valid, the SCA atomically marks the session `consumed` and issues a credential per [RFC-0003 §JWT shape](./0003-credentials.md#jwt-shape).

Response (`200 OK`):

```json
{ "shadownet:v": "0.1", "credential": "<credential JWT>" }
```

Errors:

| Status | Code | Meaning |
| --- | --- | --- |
| `400` | `csr_invalid` | CSR signature, audience, or shape failed. |
| `400` | `session_mismatch` | `sessionId` does not match CSR subject or level. |
| `409` | `session_not_ready` | Proof session is not in `ready` state. |
| `410` | `session_consumed` | Session was already used. |

### `POST /freshness`

Mint a [freshness proof](./0003-credentials.md#lifetimes-and-freshness) for a credential.

Request:

```json
{ "shadownet:v": "0.1", "credentialJti": "urn:uuid:5b7c1c4a-..." }
```

The subject-auth JWT (in `Authorization`) MUST be signed by the same DID that is `vc.credentialSubject.id` in the named credential. The SCA MUST reject if it isn't.

Response (`200 OK`):

```json
{ "shadownet:v": "0.1", "freshnessProof": "<freshness JWT>" }
```

Errors:

| Status | Code | Meaning |
| --- | --- | --- |
| `404` | `unknown_jti` | This SCA did not issue a credential with that `jti`. |
| `403` | `revoked` | Credential is revoked. |
| `403` | `not_holder` | Auth JWT subject is not the credential's subject. |

### `GET /status/<list-id>`

Returns a [BitstringStatusList](./0003-credentials.md#revocation) credential. Standard W3C VC over JWT. Cacheable per `Cache-Control`; default `max-age=300`.

### Callbacks

If `/proof/start` was called with a `callbackUrl`, the SCA SHOULD POST to it on session state transitions:

```http
POST <callbackUrl> HTTP/1.1
Content-Type: application/json
X-SCA-Callback-Sig: sha256=<hex HMAC-SHA256 of body, key=sessionId>
X-SCA-Callback-Ts:  1756682000

{ "shadownet:v":"0.1", "sessionId":"ses-01H9...", "status":"ready" }
```

The receiver MUST verify the HMAC and reject deliveries whose `X-SCA-Callback-Ts` differs from local time by more than 5 minutes. Polling remains the canonical path; the callback is an optimization.

### Re-issuance

A subject MAY re-request issuance at any time. The SCA SHOULD revoke the prior credential (set its bit in the [BitstringStatusList](./0003-credentials.md#revocation)) when re-issuing for the same level to the same subject DID.

After a [key rotation](./0002-identity.md#key-rotation), the subject presents the `KeyRotationStatement` plus a fresh CSR signed by the new key. The SCA MAY skip a new proof session if the rotation chain is valid and the original credential is still within its lifetime; otherwise a fresh proof session is required.

## Session lifecycle

| State | Transition |
| --- | --- |
| `pending` | Created by `/proof/start`. Expires 1 h after creation. |
| `ready` | Set by the SCA when proof completes. Expires 1 h after becoming `ready`. |
| `consumed` | Set atomically by a successful `/issuance`. Terminal. |
| `failed` | Set by the SCA if proof was rejected. Terminal. |
| `expired` | Set when TTL elapses without state change. Terminal. |

A subject MUST start a fresh session if their previous one is `failed` or `expired`.

## Policy document

`method` values are **operator-defined URIs**. The protocol does not enumerate or mandate any specific proof methods — an SCA may use email verification, government-ID document checks, biometric kiosks, in-person verification, an enterprise directory, single-sign-on with a third party, or any combination. Verifiers identify methods only by their URI; semantics are out of scope for this RFC.

```json
{
  "issuer": "did:web:sca.shadownet.example",
  "shadownet:v": "0.1",
  "levels": [
    {
      "level": "urn:shadownet:level:L1",
      "method": "urn:example-sca:method:email-verification",
      "rateLimit": "1 per email per 24h",
      "credentialLifetimeDays": 90
    },
    {
      "level": "urn:shadownet:level:L2",
      "method": "urn:example-sca:method:stripe-identity-document-check-v1",
      "credentialLifetimeDays": 365
    }
  ],
  "freshnessWindowSeconds": 86400,
  "statusListBase": "https://sca.shadownet.example/status/"
}
```

The example method URIs above are illustrative. Real method URIs are defined by each SCA operator under their own URN namespace.

The policy is normative for the SCA's own behavior. Verifiers MAY use it to display human-readable reasoning ("this credential is L2, verified by an external ID-check provider").

## Trust store

A verifier's trust store is a list of `(issuer DID, accepted levels)` entries:

```json
[
  {
    "issuer": "did:web:sca.shadownet.example",
    "acceptedLevels": [
      "urn:shadownet:level:L1",
      "urn:shadownet:level:L2",
      "urn:shadownet:level:O1"
    ]
  }
]
```

Trust stores are local to each verifier. The reference Sidecar ships with the v0.1 cloud SCA as the only entry. Users MAY add or remove entries.

The protocol does not specify a global root-store program. A future RFC may define one.

### Required-level predicates

Interactions and verifiers express what credentials they need as a JSON predicate:

```
predicate ::= leaf | "all" | "any" | "not"

leaf      ::= { "level":       <level-URI> }
            | { "issuer":      <issuer-DID> }
            | { "subjectType": "person" | "organization" }

"all"     ::= { "all": [ predicate, ... ] }   ; logical AND, ≥1 child
"any"     ::= { "any": [ predicate, ... ] }   ; logical OR,  ≥1 child
"not"     ::= { "not": predicate }
```

Examples:

```json
// L2 OR L3
{ "any": [
  { "level": "urn:shadownet:level:L2" },
  { "level": "urn:shadownet:level:L3" }
]}

// any organization credential
{ "subjectType": "organization" }

// L2 issued specifically by sca.shadownet.example
{ "all": [
  { "level":  "urn:shadownet:level:L2" },
  { "issuer": "did:web:sca.shadownet.example" }
]}
```

#### Evaluation

A presentation `P` (containing one or more credentials) satisfies a predicate `R` iff:

- For a leaf `R`, **at least one** credential in `P` matches `R` AND that credential passes all integrity checks (signature, expiry, freshness, revocation).
- For `{ "all": [R₁, …, Rₙ] }`, every `Rᵢ` is satisfied (possibly by different credentials in `P`).
- For `{ "any": [R₁, …, Rₙ] }`, at least one `Rᵢ` is satisfied.
- For `{ "not": R }`, `R` is *not* satisfied.

There is no implicit ordering between levels. `L2` does NOT imply `L1`. If a verifier wants tier semantics it MUST enumerate them explicitly via `any`.

Maximum predicate depth is 4. Deeper predicates MUST be rejected as `predicate_too_deep`.

### Trust evaluation

When verifying a presentation that contains a credential `C`:

1. Look up `C.iss` in the trust store. If absent, `C` is untrusted.
2. Check that `C.vc.credentialSubject.level` is in the issuer's `acceptedLevels`. If not, `C` is untrusted at this verifier's policy.
3. Validate signature, expiry, freshness, and revocation per [RFC-0003](./0003-credentials.md).
4. Evaluate the interaction's required-level predicate against the full presentation per the rules above. If unsatisfied, return `level_insufficient` (RFC-0006).

## Revocation by the SCA

Beyond re-issuance, an SCA SHOULD revoke a credential when:

- The subject explicitly requests revocation (e.g. account closure).
- The SCA learns the underlying proof was fraudulent.
- The subject's key is reported compromised and no rotation has occurred.

Revocation is published via the BitstringStatusList. Revoked credentials remain visible in the list (the bit stays set); they are not deleted.

## Multi-SCA semantics

A subject MAY hold credentials from multiple SCAs simultaneously (for example, an `L2` from the cloud SCA and an `O1` from their employer's SCA). The holder presents whichever is relevant to the interaction. Verifiers evaluate each credential independently against their trust store.

## Open questions

- Whether `/issuance` should accept a JWT that bundles the `sessionId` + CSR in one signed envelope (single round trip).
- Cross-signing (one SCA endorses another) — useful, deferrable.
- Auditability: append-only issuance log à la Certificate Transparency. Deferred; the protocol allows it via a future `vc.credentialStatus.transparencyLog` field.
