# RFC 0005: Shadow Name Service

## Summary

SNS resolves a human-readable Shadowname to the data needed to open an A2A connection: a DID, an endpoint URL, and a current public key. Modeled after DNS — multiple providers, cacheable records, signed responses.

## Shadowname grammar

```
shadowname  = local "@" provider
local       = 1*63 ( ALPHA / DIGIT / "_" / "-" / "." )    ; case-insensitive
provider    = host                                         ; an SNS provider domain
```

Examples: `mahdi@sh4dow.org`, `acme@sh4dow.org`, `events@acme.example`.

The `@`-shape encodes which provider is authoritative for the name. Comparing names is case-insensitive on `local`; canonical form is lowercase.

A Shadow MAY have multiple Shadownames (aliases). The DID is the stable identity.

## Records

```json
{
  "shadowname": "mahdi@sh4dow.org",
  "did":        "did:key:z6MkSubjectPubkey...",
  "endpoint":   "https://shadow.sh4dow.org/u/mahdi/a2a",
  "publicKey":  { "kty": "OKP", "crv": "Ed25519", "x": "<base64url>" },
  "subjectType": "person",
  "ttl":        300,
  "issuedAt":   1759200000,
  "shadownet:v": "0.1"
}
```

The record is signed by the SNS provider. The signed wire form is a JWT:

```json
{
  "iss": "did:web:sns.sh4dow.org",
  "sub": "mahdi@sh4dow.org",
  "iat": 1759200000,
  "exp": 1759200300,
  "shadownet:v": "0.1",
  "record": { ...the JSON above... }
}
```

`exp - iat` MUST equal the record's `ttl`.

## Resolution endpoint

A v0.1 SNS provider MUST expose:

```
GET https://<provider>/.well-known/sns/v1/resolve?name=<shadowname>
Accept: application/jwt
```

Response: `200 OK` with the signed JWT in the body, `Content-Type: application/jwt`.

Errors:

| Status | Meaning |
| --- | --- |
| `404` | No such Shadowname at this provider. |
| `410` | Shadowname existed and was deleted. (Tombstone.) |
| `429` | Rate limited. |

## Resolution flow

```
Caller                                     SNS provider
   │                                              │
   │  1. parse shadowname → (local, provider)     │
   │                                              │
   │  2. GET https://<provider>/.well-known       │
   │     /sns/v1/resolve?name=local@provider ───►│
   │                                              │
   │ ◄────── 3. signed record JWT ────────────────│
   │                                              │
   │  4. verify provider DID + signature          │
   │  5. cache until exp                          │
   │  6. open A2A to record.endpoint              │
```

Callers MUST verify the signature against the provider's `did:web` (resolved per [RFC-0002 §did:web](./0002-identity.md#did-web--organizations)) before trusting the record.

## Caching

- Records are cached until `exp`.
- Negative responses (404) SHOULD be cached for at most 60 s.
- Resolvers MUST respect `Cache-Control: no-store` if present.
- `ttl` SHOULD be ≥ 60 s and ≤ 86400 s. The recommended default is 3600 s; see [§Lifecycle](#lifecycle) for the renewal rationale.

## Lifecycle

A record's signed JWT envelope is time-bounded by `iat` / `exp` (with `exp - iat == ttl`). This section defines the SNS provider's obligations across that lifetime and the subject's renewal model.

### Wire invariant

A successful resolution response (`200 OK` with a signed JWT body) MUST carry an envelope whose `exp` is strictly greater than wall-clock at response time. Servers MUST NOT serve pre-expired records. A server faced with a stored record whose envelope has expired MUST either refuse the resolution (404) or re-issue the envelope (see [§Server re-issuance](#server-re-issuance)) before returning `200`.

A resolver that receives a `200` response whose envelope `exp` is in the past at the time of verification MUST treat the response as if the resolution failed; the resolver SHOULD surface the failure as a distinct error class from "no such name" or "malformed record" so callers can branch on transient vs. permanent failures.

### Server re-issuance

A server MAY re-mint the signed JWT envelope on every resolution, stamping fresh `iat = now` and `exp = now + record.ttl`, **provided** the underlying record data (DID, endpoint, public key, subject type) still reflects the subject's most recent authenticated registration (`PUT /v1/records/<local>`). Under this model, TTL functions as a resolver-side cache hint; records do not age out at the wire boundary.

A server MAY alternatively store the original signed JWT bytes at registration time and serve them verbatim until `exp`. Under this model, records expire at the wire boundary and the subject is responsible for re-registering before `exp`.

A server MUST NOT extend `iat` of a record without a contemporaneous authenticated `PUT` from the subject (or a sweeper acting on the subject's behalf under a documented operator policy). Re-issuance is a re-signing of the *same* subject-authorized data; it is not a way to keep a deleted, tombstoned, or unauthorized record alive.

### Client-side renewal

When the server uses the store-and-serve model, the subject is responsible for keeping its record resolvable. Subjects SHOULD re-register (`PUT /v1/records/<local>`) before `iat + ttl - max(60, ttl / 10)` seconds wall-clock. The grace window absorbs clock skew, in-flight requests, and queue latency in subject-side renewal workers.

Subjects SHOULD NOT rely on the re-issuance model being available at a given provider unless that provider's documentation guarantees it. The renewal pattern works against either provider model; the re-issuance model removes the requirement but not the option.

### Distinct expiry surface

Resolvers SHOULD distinguish, in their language-native error taxonomy, between:

- **Malformed or unsigned-by-the-claimed-provider record** — caller bug or attack; not re-resolvable.
- **Expired record** — transient; the subject may have a renewal in flight, and a retry after a small backoff (or after invalidating the resolver's positive cache) may succeed.

This is a SHOULD because the spec does not mandate a particular language API; the existing wire surface already conveys expiry via the JWT `exp` claim.

## Identity update

When a subject rotates keys (per [RFC-0002 §Key rotation](./0002-identity.md#key-rotation)):

1. The subject submits an authenticated `PUT /v1/records/<local>` to its SNS provider, signed by the **new** key, with the `KeyRotationStatement` attached.
2. The SNS provider verifies the rotation chain and publishes a new record with the new DID and key.
3. Cached old records expire naturally; cooperating providers MAY publish a short-TTL "see new record at" hint.

## Gateway pattern

The `endpoint` URL in an SNS record names where peers send A2A traffic. Nothing in the protocol requires that endpoint to be the Subject's actual Sidecar — it MAY be a **gateway** that performs cheap, rules-only filtering (VP validation, contact-graph lookup, affiliation check, rate limiting, abuse signal detection) and forwards accepted traffic to a backend Sidecar that may not itself be publicly addressable. This mirrors the email MX pattern: a domain's MX record points at a provider that handles inbound delivery, spam filtering, and routing before traffic reaches the actual mailbox.

```
peer's Shadow ──A2A──► [Gateway @ SNS endpoint] ──auth-forward──► [Backend Sidecar]
                              │
                              ├─► unknown sender   → quarantine (see RFC-0006)
                              ├─► spam / abuse     → flagged, surfaced to user (never auto-deleted)
                              └─► rate limits      → 429
```

Properties of the gateway role:

- **Substitutable.** A Subject can change gateway providers by re-publishing the SNS record with a new `endpoint` (and key). Backend Sidecars do not need to change. This makes the gateway an MX-equivalent commodity.
- **Cheap by construction.** Gateways MUST NOT invoke the host agent's LLM on inbound traffic. All gateway decisions MUST be rules-based. The cost guarantee in [RFC-0006 §Routing and quarantine](./0006-a2a-profile.md#routing-and-quarantine) flows from this property.
- **Spam handling is the gateway's job.** Gateways MAY flag traffic as suspected spam or abuse, MAY rate-limit, and MAY queue quarantined items for user review. Gateways MUST NOT silently discard inbound traffic — the user retains the final choice of whether to see, quarantine, or block a sender. Documented denylists (e.g. cryptographic IDs of known abuse networks) MAY result in early rejection, but the rejection MUST be observable in the Subject's quarantine surface, not invisible.
- **Authentication between gateway and backend** is out of scope for this RFC. Reference deployments commonly use mTLS or signed forward headers; either works.

Deployment shapes:

- **Personal Shadow on a public provider** (e.g. `mahdi@sh4dow.org`) — gateway and backend are the same process at the public provider. Quarantine and inbox live together.
- **Personal Shadow, self-hosted backend** — SNS endpoint points at a public provider's gateway; backend Sidecar runs on the user's hardware. The gateway forwards only known-contact traffic to the backend.
- **Enterprise Shadow** (e.g. `bob@acme.example`) — gateway runs on the enterprise's infrastructure (or a contracted provider). Inbound from outside the org is policy-checked; inbound from inside the org (same-affiliation) is forwarded with a fast path. Backend Sidecars may be per-employee or shared multi-tenant.

The gateway pattern is normatively permitted but not required. Single-process Sidecars that combine all three roles are conformant.

## Endpoint privacy

The `endpoint` URL leaks the provider that hosts the Shadow. v0.1 accepts this leak (it mirrors how an email address reveals the user's mail provider). A future RFC may define rendezvous endpoints to hide the actual host.

When a gateway fronts a backend Sidecar, the endpoint URL leaks only the *gateway* — the backend's address is not advertised. This is a privacy improvement over single-process deployments and SHOULD be considered when self-hosting.

## Multiple SNS providers

Nothing in this RFC requires a single global SNS. Two Shadows under different providers (`mahdi@sh4dow.org` and `bob@acme.example`) interoperate as long as their resolvers can reach each other's providers' `/.well-known/sns/v1/resolve` endpoints.

A provider's reputation is established the same way an SCA's is: verifiers maintain a local trust list, default-populated by the reference deployment.

## Open questions

- Whether a single `GET /v1/batch?names=a@x,b@y` is worth defining for clients that resolve many names at once (the Birthday flow does).
- Whether records should also list the SCAs the subject holds credentials from (avoids one round trip during A2A handshake — but couples SNS to credential lifecycle).
- A canonical denial-of-existence proof for negative caching (similar to NSEC in DNSSEC) — likely overkill for v0.1.
